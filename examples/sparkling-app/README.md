# Solid × Lynx × Sparkling — a real app

This is not a web demo. It is a **Lynx app that builds an APK, runs on a real
device and uses native routing**, with the UI written in Solid 2 through this
repository's runtime.

```
tailwind.config.ts          ─┐
src/pages/main/index.tsx    ─┤  rspeedy + pluginSolidLynx + Tailwind
src/pages/second/index.tsx  ─┤
                             ▼
                main.lynx.bundle / second.lynx.bundle
                             │  copy-assets
                             ▼
        android/ (Sparkling native shell) ──► app-debug.apk
```

- `android/` — the native shell generated by Sparkling 2.0.1: Kotlin, Gradle,
  the LynxView container, native routing and the splash screen.
- `app.config.ts` — Sparkling's app manifest, which also carries the Rspeedy
  build config (`lynxConfig`).
- `lynx.config.ts` — a direct entry for the raw `rspeedy` CLI, equivalent to
  the file the CLI generates under `.sparkling/`.
- `tailwind.config.ts` — the Lynx Tailwind preset plus this app's color tokens.
- `scripts/android.mjs` — one command for bundle → copy assets → Gradle →
  install/launch.
- `scripts/copy-assets.mjs` — copies `dist/` into the Android assets; Android
  only, so no stray iOS tree is created.

Verified on a Kirin 970 device: first frame,
signal updates, native route into `second.lynx.bundle`, and `close()` returning
with the main page state intact.

## Why this is generic

Sparkling only asks two things of the frontend:

1. the native shell has a LynxView container;
2. the container loads `*.lynx.bundle` files from `assets`.

It does not care whether those bundles come from ReactLynx, Solid, Vue or
hand-written Lynx. `sparkling-app-cli build` really does two steps (see
`node_modules/sparkling-app-cli/dist/commands/build.js`):

```js
await runCommand('rspeedy', ['build', '--config', tempConfig])
await copyAssets({ source: 'dist', androidDest: 'android/app/src/main/assets' })
```

So **any build that produces `.lynx.bundle` can plug in here**. This example
uses `@lynx-solid/plugin`.

The only Solid-specific difference from a ReactLynx template:

```diff
- pluginReactLynx()
+ pluginSolidLynx()
```

and the entry changes from `root.render(<App />)` to `render(() => <App />)`.
Routing, scheme handling and native methods stay the same.

## Styling: Tailwind v3, not web Tailwind

The pages use utility classes; `src/App.css` keeps only the `@tailwind`
directives and the page gradient.

- Tailwind **v3** is required: `@tailwindcss/postcss` (v4) conflicts with
  `rsbuild-plugin-tailwindcss`.
- `@lynx-js/tailwind-preset` is experimental and only covers the CSS that Lynx
  supports. There are no hover, focus or media-query variants.
- JIT scans source statically: runtime-built names such as `bg-${color}` are
  never generated. Write the complete class string or use a safelist.
- Measured cost of the migration: +2.0 kB per bundle (main 91.6 → 93.6 kB,
  second 88.4 → 90.4 kB).

## Version bridge (the only non-standard part)

Sparkling 2.0.1 pins Rspeedy 0.13 / Rsbuild 1.7, while `@lynx-solid/plugin`
needs Rsbuild 2. `package.json` therefore declares:

```diff
- "@lynx-js/rspeedy": "^0.13.3"
+ "@lynx-js/rspeedy": "^0.18.5"   // Rsbuild 2.3.2
```

`pluginSolidLynx()` checks whether the `lynx:rsbuild` plugin is already
registered (`isPluginLynxRegistered`) and skips duplicate initialization.

> Once Sparkling's template moves to Rsbuild 2, this pin can be deleted. It is
> a version bridge, not an architectural hack.

## Environment

| Dependency | Version |
|---|---|
| Node | 22 or 24 (26 builds, but `sparkling doctor` rejects it) |
| JDK | 17 |
| Android SDK | platform 34, build-tools 34.0.0, platform-tools |
| adb | on `PATH` |

`ANDROID_HOME` points at the SDK root (the directory containing `platforms/`,
`build-tools/` and `platform-tools/`).

The build resolves `JAVA_HOME` and `ANDROID_HOME` through
`scripts/toolchain.mjs`: `.env.local` (gitignored) first, then the environment,
then `android/local.properties` and common install locations. Run
`nub run toolchain` to print what it found; copy `.env.example` to `.env.local`
if your toolchain lives elsewhere. `nub run android` applies the same lookup to
its child processes, so no shell exports are required.

### SDK platform 34

Install `platforms;android-34` — the plain base platform, not one of the
`platforms;android-34-extN` extensions. AGP 7.4 reads
`AndroidVersion.IsBaseSdk` from the platform's `source.properties`, and an
extension renamed to `android-34` fails with
`Cannot invoke "java.lang.Integer.intValue()" ... mExtensionLevel is null` or
`Failed to find target with hash string 'android-34'`.

The example adds two compatibility tweaks:

- `android.builder.sdkDownload=false` in `android/gradle.properties` turns a
  missing SDK component into an immediate error instead of a multi-minute
  hang on `dl.google.com`.
- `android/build.gradle.kts` pins `buildToolsVersion` to `34.0.0` for every
  subproject: AGP 7.4 defaults to 30.0.3 for modules that do not declare one
  (`sparkling-navigation`), which would download an extra copy.

## Run it

```bash
nub install
nub run build       # bundles + copy assets into android/app/src/main/assets
nub run android     # gradle assembleDebug; installs and launches if a device is attached
```

Artifact:

```
android/app/build/outputs/apk/debug/app-debug.apk
```

To iterate on JS only (no native rebuild):

```bash
nub run dev         # Rspeedy dev server + QR code
# scan it with Lynx Explorer, or paste the bundle URL
```

## Cold start: debug is slow, not Solid

Measured on the same Kirin 970 device with `adb shell am start -W`,
after `force-stop`, three runs:

| Build | `TotalTime` |
|---|---|
| debug (template default) | 1149 / 1150 / 1179 ms |
| release (debug-signed, no R8) | 388 / 390 / 434 ms |

To confirm this is not Solid, the same `android/` shell was built with the
official ReactLynx template's bundle (`main` bundle 106 KB; Solid is 92 KB):

| | debug | release |
|---|---|---|
| Solid | ~1.15 s | **~0.40 s** |
| ReactLynx | ~1.30 s | ~0.55 s |

The white screen came from Sparkling's debug build: Lynx devtool, logbox and
the debug engine are all on, and R8 is off. Solid is slightly faster than
ReactLynx (smaller bundle, lighter runtime).

The example makes three launch-related changes:

1. **`AppLaunchTheme`** (`res/values/styles.xml`). The template had no theme,
   so the system starting window used AppCompat's white background and an
   action bar — that was the visible "white screen + title bar". Now
   `windowBackground`, the status bar and the navigation bar use the first
   gradient color `#0F172A`, so the starting window matches the first frame.
2. **Background Fresco init.** `Fresco.initialize()` costs ~400 ms on the main
   thread and only serves `<image>`, which the first frame does not need. It now
   runs on the `fresco-init` thread, in parallel with Lynx init, and finishes
   before the first image request.
3. **Release signed with the debug keystore.** Only so `installRelease` can
   replace `installDebug` on a test device. **It is not a publishing key** —
   replace it before shipping.

Run release locally:

```bash
cd android && SPARKLING_USE_NATIVE_ASSETS=true ./gradlew.bat installRelease
```

Measure a real cold start:

```bash
adb shell am force-stop com.lynxsolid.demo
adb shell am start -W -n com.lynxsolid.demo/com.example.sparkling.go.SplashActivity
# read TotalTime
```

## Known limitations

1. **Two Windows CLI bugs.** `sparkling-app-cli` 2.0.1 spawns `rspeedy`
   without a shell, so Windows cannot resolve `rspeedy.cmd`; its `autolink`
   also passes an absolute path to the ESM loader and fails with
   `ERR_UNSUPPORTED_ESM_URL_SCHEME`. `scripts/android.mjs` works around the
   first with `shell: true`; the second falls back to the default directory
   layout, which is what this example uses.
2. **`sparkling doctor` is unreliable here.** It can report the JDK as missing
   even when `java -version` works (it only reads stderr when the child throws,
   but `java -version` exits 0 with its output on stderr), and it rejects
   Node 26. Trust `nub run build` / `nub run android` instead.
3. **The 2.0.1 template has no dev-URL input screen.** Use Lynx Explorer for JS
   hot reload on a device; native changes require a rebuild.
4. **The native engine is Lynx 3.6.0.** Our bundles target SDK 3.2, which is
   backward compatible. Moving to the 4.x engine means upgrading
   AGP/Kotlin/Gradle together and is out of scope for this example.
5. **The JDK toolchain is 17.** The template forces JDK 11 in
   `android/build.gradle.kts` (`targetJavaVersion` / `jvmToolchain`) and
   `android/app/build.gradle.kts` (`sourceCompatibility`, `targetCompatibility`,
   `jvmTarget`). The example uses 17 so one JDK is enough; change all five
   pins to 11 if your environment cannot install 17.
6. **APK size.** The debug APK is ~70 MB because `abiFilters` includes both
   `arm64-v8a` and `armeabi-v7a` and minify is off. Keeping only `arm64-v8a`
   (in `android/app/build.gradle.kts`) roughly halves it; ship with
   `assembleRelease` + R8.
7. **Android only.** The example ships the Android shell and nothing else;
   `nub run build` writes straight into `android/app/src/main/assets`, and
   `autolink` runs with `--platform android` so it cannot recreate an iOS tree.
   Sparkling's generator (`create-sparkling-app` / `sparkling-app-cli`) can
   produce the iOS shell from the same template, and `src/pages/**` is
   platform-agnostic — but this example has no macOS to verify any of it.

## Publishing

```bash
keytool -genkeypair -v -keystore release.jks -keyalg RSA -keysize 2048 \
  -validity 10000 -alias app

# configure signingConfigs in android/app/build.gradle.kts, then:
cd android
gradlew.bat assembleRelease
```

To use an IDE, open `android/` in Android Studio; the example itself does not
depend on Studio.

## Who this is for

- **Shipping Solid on Lynx**: edit `src/pages/**` and keep the rest.
- **Using Vue/Svelte**: swap `pluginSolidLynx()` for the matching plugin;
  `scripts/android.mjs` and `android/` stay as they are.
- **Hooking a custom build into Sparkling**: read `scripts/android.mjs` and
  `lynx.config.ts`; they take the CLI's black box apart.
