# 基准测试

> **本页所有数字均来自真机。** 这里的仪器只度量**产物体积**与**真机行为**，没有任何浏览器侧测量。

两条轴，都便宜到可以随时重跑：**包有多大**，以及**多久内容上屏**。

## 被测对象

一份 js-framework-benchmark 风格的 table workload，两套**各自惯用**的实现（与 vue-lynx-vapor 的 ui-vdom/ui-react 同构，即 [vue-lynx](https://github.com/Huxpro/vue-lynx) 的 vapor 分支，Apache-2.0）：

| | lynx-solid | ReactLynx |
|---|---|---|
| 状态 | `createStore` draft 变更（细粒度 signal） | `useState` 不可变替换 + `memo(Row)` |
| 列表 | `<For>` 按引用做 key | `key={id}` + preact diff |
| 入口 | `examples/bench-table` | `examples/bench-table-react` |

两者共享逐字节一致的 DOM 契约（`.rows` / `.row` / `.danger` / `.col-label` / `.btn-text`）。

**ReactLynx 是对照系**，不是被测主体：我们用它标定「一个成熟的双线程框架会打出多少字节」。

## 仪器

| 仪器 | 回答什么 | 量纲 |
|---|---|---|
| 离线包体普查（`sweep:examples`） | 产物有多宽 | 纯 `fs` + `zlib`，不碰任何宿主 |
| 真机冷开（`sweep:device`） | 多久内容上屏 | Android 设备：Explorer 冷启 + LAN 取包 + 双线程求值渲染 |
| 真机自检（`test:device`） | 原生宿主上行为是否正确 | Android 设备，6 条行为断言 |

这里**没有任何浏览器测量**。**禁止跨仪器做比值**——字节不是毫秒，冷开包含 Explorer 启动与 LAN 取包，那是其它量纲里没有的。

## 包体体积

`nub run -F @lynx-solid/benchmark sweep:examples` —— 离线扫 `examples/*/dist`，**33 个入口**（32 个带 web 预览对照 + `raw-lynx`，后者无 web target）。

| | lynx gzip | lynx raw |
|---|---|---|
| 最小 | **7,993**（`raw-lynx`） | 15,075 |
| 中位 | **38,380** | — |
| 最大 | **152,325**（`elk`） | 484,690 |

`mini-pure` 落在 15,731 gzip——它是带 web 对照的入口里的下限；其余都从 33,500 起步。

原始表里的 `web gzip` 是**文档预览载荷**，不是运行时开销——web target 存在只是为了 `<Go>` 和 `compile-lab` 能预览，真机下载的不是它。

对照组（同一次运行、同一台仪器）：

| bundle | lynx raw | lynx gzip | web gzip |
|---|---|---|---|
| `bench-table`（solid） | 121653 | 47034 | 40808 |
| `bench-table-react`（ReactLynx） | 97740 | **41055** | 32791 |

此处 solid 的 gzip 是 ReactLynx 的 **1.15×**——rc.6 那次还是 1.04×；变化来自 Solid 侧升级到 solid-js 2.0 rc.18 并改用 ES2017 设备基线，ReactLynx 侧未变。

> 两份 bundle 都不含 polyfill：真机运行时基线是 ES2020 内建加引擎 API（`queueMicrotask` 由入口垫片提供）。`tests/behavior/device-baseline.test.ts` 会扫描源码中的 `core-js` 与 ES2021+ 缺口来守住这条。

## 冷开 → 内容

`nub run -F @lynx-solid/benchmark sweep:device` —— **33/33 ok、0 DNF、0 errors**，设备为一台 Snapdragon 8 Gen 3 安卓机（Android SDK 36），每入口 3 次取中位。

方法：`am force-stop com.lynx.explorer` → `logcat -c` → `lynx://open?url=…` → 轮询两条独立通道：
- **logcat**（本轮 33/33 行）—— 引擎里程碑 `__OnAppFirstScreen`，按优先级对照 `OnPatchFinishForFiber` / `__OnNativeAppReady`，每个入口单独对齐主机与设备时钟（本轮 `clockOffset` 2475 ms）
- **screencap**（兜底，本轮未触发）—— 8–92% 中带 PNG 内容评分，跳过 600 ms 的 Explorer 窗口过渡

因此 `open → content` **包含 Explorer 冷启 + LAN 取包 + BG 求值渲染 + IPC 应用**，它不是框架渲染时间。

| | ms |
|---|---|
| 中位 | **346** |
| 最小 / 最大 | 309 / 479 |
| 最慢 | `motion/spring` 479、`scrolling/ListFilter` 475、`scrolling/ListReorder` 449 |
| 最快 | `counter` 309、`motion/motion-value` 309、`7guis/temperature-converter` 316 |

33 个入口全部落在 **309–479 ms** 区间——包体体积相差 17 倍，冷开时间却只差约 1.5 倍，即冷开主要由 Explorer 启动和 LAN 取包决定，跟包多大、哪个框架打的无关。

### 被标记的行——不重跑不要引用

`harness/sweep-device.mjs` 会把这类**自动**写进报告的 `notes` 列（`rowNotes()`），判据由 bundle 字节与两条通道算出，不依赖人手写脚注：

- **mini-pure** —— 3 轮 `screencap` 全为 null。313 ms 是*引擎里程碑到达*，不是*内容可见*，所以不能被引为最快条目。

**非产线构建会在进入测量之前被挡掉。**`prepare-examples` 会硬拦带有 dev 构建标记的 `dist/`，`rowNotes()` 还会从 bundle 字节再检一遍同类问题——所以数据一旦回退会自己标出来，不会悄悄通过。

完整表：[`results/examples-sweep-device.md`](https://github.com/lynx/lynx-solid/tree/main/packages/benchmark/results/examples-sweep-device.md)

## 真机自检

`nub run -F @lynx-solid/benchmark test:device` —— 一台 Snapdragon 8 Gen 3 安卓机，全部用例通过。`open → content` **415 ms**，页面内渲染标记 **51 ms**（BG 模块求值 → mount 稳定，不含取包与 Explorer 启动）。

| 用例 | 结果 | 详情 |
|---|---|---|
| bg-bare-settimeout | PASS | fired; `globalThis.setTimeout=undefined` |
| bg-timer-args-observe | PASS | fired; `args(2)=["null","0"]` |
| bg-queue-microtask | PASS | guard 自己的 JS 箭头，转调 `lynx.queueMicrotask`（只能经裸绑定拿到——BG 上没有 `lynx` 全局） |
| bg-microtask-ordering | PASS | guard 的全局与引擎 fn 都跑在先前排的 `setTimeout(0)` 之前；两级 `Promise.then` 链**没有**（这里的 `Promise` 是 JS polyfill） |
| mt-queue-microtask-guard | PASS | 前后均为 `function [native code]`——是**宿主**提供的，两臂一致 |
| template-static-render | PASS | mounted in 51.0ms |
| unmount-oncleanup | PASS | fired |
| sign-event-bindtap | PASS | tap received, counter=1（1212 ms） |

前三条正是「web 宿主 ≠ 真机宿主」的坑：真机定时器经 `js_app.cc` 绑定会丢掉转发的参数，而 `queueMicrotask` 在原生宿主上不是裸全局，得由入口垫片装上。

**真机上的 `queueMicrotask`。** BG 没有 `queueMicrotask` 全局：runtime 装一个，转调 `lynx.queueMicrotask`，而它只能经**裸标识符**拿到（`lynx` 是 `RuntimeWrapperWebpackPlugin` 注入的参数——BG 的 `globalThis` 上没有 `lynx`）。MT 的 JS 上下文自带 `queueMicrotask`，所以 guard 在那里是空操作。`Promise` 在这个宿主上是 JS polyfill、**不是** microtask 原语（第二级 `.then` 会输给 `setTimeout(0)`），所以需要真实 checkpoint 的地方（Solid 调度、`internal/microtask.ts`）必须走 `queueMicrotask`/`lynx.queueMicrotask`。以上在一台 Kirin 970 设备 / Lynx SDK 4.0 上实测。

**`mt-queue-microtask-guard` 量的是 MT 上下文**，`queueMicrotask` 由它自带——runtime 在 MT 上什么都不装。`--ifr` 只是选包（IFR 臂在 `dist-ifr/`，记录写 `device-selftest-ifr-latest.*`），两臂读数相同。

> **`--tap-x` / `--tap-y` 必须传**，否则 `sign-event-bindtap` 必挂。两者默认为空，不传时 runner 根本不发 tap，等满 15 s 后失败——报错文案 `no tap within 15000ms` 与权限无关。坐标随设备/布局变化（本次使用的设备上是 `265 509`），先在自己的设备上定位按钮坐标。

## 目前没有测

- **交互延迟**（点击 → 上屏终态）—— 需要真机点击注入加原生终态谓词。web harness 有一套（`__x.arm` 按 rAF 轮询 composed DOM），真机侧还没有对应物，因此本页**不作任何延迟断言**。`device-lab` 的 `sign-event-bindtap` 测的是等待时长，不是点击→渲染延迟，不要拿它当延迟数字。
- **JS heap** —— 此前只来自 Chromium CDP，真机侧没有埋点。
- **多设备** —— 以上全部来自同一台手机、同一局域网。

## 复现

```bash
nub run -F @lynx-solid/benchmark sweep:examples   # 离线包体普查
nub run -F @lynx-solid/benchmark sweep:device     # 冷开（需设备在同一局域网）
nub run -F @lynx-solid/benchmark test:device --tap-x 265 --tap-y 509   # 行为自检
```

原始数据：[`packages/benchmark/results/`](https://github.com/lynx/lynx-solid/tree/main/packages/benchmark/results)（`examples-sweep.json`、`examples-sweep-device.json`、`device-selftest-latest.json`，均已入库）。

> - `sweep:device` / `test:device` 要求设备在同一 Wi-Fi 局域网（`adb devices` 非空）。无线端口中途轮换时 harness 会走 mdns 重发现——旧端口显示 `offline`，继续重试那个旧端口是没用的。
> - MIUI 上点击注入还需打开「USB调试（安全设置）」，另见上面 `--tap-x`/`--tap-y` 的说明。
> - dev server 的产物写在 `examples/*/dist-dev/`，`dist/` 只有产线构建 ⇒ 跑这些时可以开着 dev server。
